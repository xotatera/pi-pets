### Isolated official Linux package inspection (owner authorized)

- Runtime: rootless Podman Linux/amd64 container (Arch image), no host home mounts or credentials. Downloaded only the official `https://persistent.oaistatic.com/codex-app-prod/linux/deb/pool/main/c/chatgpt/chatgpt_26.930.21537_amd64.deb` linked by the official [OpenAI Linux APT package index](https://persistent.oaistatic.com/codex-app-prod/linux/deb/dists/stable/main/binary-amd64/Packages). Package index reported size `475227490` and SHA-256 `60fdb6d895d776f8831ff35a783de04cdbfa280f0f3d972584315f98e57aa256`; archive hash checked before extraction. Installed/extracted inside the pod without launching the app. Installed `@openai/codex@0.160.0` CLI separately in that pod. No copy of app binaries/assets was added to the repo.
- Static `app.asar` inspection finds `webview/assets/*-spritesheet-v*.webp`, `use-avatar-options`, `pets-settings-route`, and `pet-content`. The latter consumes `accessoryId` from an in-app account settings query and resolves `pet_*` entries from a `/pets` account query, including `spritesheet_url` and `spritesheet_url_expires_at`. The bundled app's mapping reads `settings.accessory_id` in an account/user settings response. It is **not** a documented public settings API for Pi to call and does **not** prove a locally persisted authoritative mirror. Built-in spritesheets packaged in the app do not prove a stable filesystem location or supported copy license.
- Inspection was static and unauthenticated: it did not start the UI, log in, read user data, confirm what happens on logout/offline, or test account sync against Codex App/CLI. The session's prior CLI-local `tui.pet` is not this account field. This evidence makes guessing a local mirror *less* justified, not more. macOS/Windows app bundles cannot be inferred from this Linux package.

### Public online API check (owner-requested)

- Searched public OpenAI/Codex issue references and OpenAI developer API documentation for a documented read-only pet-selection or `accessory_id` endpoint. **No documented public pet-settings API was located**; that is a bounded research result, not proof no endpoint exists. The Linux app bundle's `settings.accessory_id` and `/pets` account calls are internal implementation details, not a stable public contract.
- Pi's packaged [`openai-chatgpt` OAuth implementation](../../../../node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-chatgpt.js) (local development dependency; source URL is not distributable with docs) requests the resource `https://api.openai.com/v1` and scope `chatgpt.tokens.use.direct`. It documents a token for OpenAI Responses API use, not permission to call ChatGPT desktop's account-settings service. A qualifying login in Pi therefore does **not** establish that Pi may access the desktop setting. No token was accessed, copied or tested against any endpoint.
- Safe next step if owner changes scope: implement independently verified offline Linux CLI/desktop pet imports while deferring the linked profile; alternatively obtain an officially supported read-only account-settings contract and authorization model. Never call an internal ChatGPT backend endpoint or read another app's auth/database just because its bundle mentions that endpoint.

### Owner-authorized interactive verification (Linux only)

The owner requested an actual login check. Installed the hash-verified official Linux package version `26.930.21537` in a separate disposable **rootless Podman** container with an isolated Xvfb browser, a temporary-password VNC page bound to `127.0.0.1`, no host home/display mounts and no collected app logs. The owner entered their own login through the UI; credentials were never provided to the agent or read from the pod. On the app's **Mini & Pets** settings screen, an account-selected custom pet and several account pet choices were visible. No user pet names, account identifiers, screen captures or artwork are included in this repository.

Pet-only inspection after login found `~/.codex/pets` present but **zero** `pet.json` manifests or spritesheets; `~/.codex/avatars` and the CLI's built-in spritesheet cache were absent in this pod. No general app databases, browser cache, auth stores, chat data, or account requests were inspected. This demonstrates the UI works and selection is available *inside the logged-in app*, **not** that Pi can read a stable local pet selection or all cloud pet artwork without app-internal services. Once inspected, the container (including its account session) was force-stopped and removed, and the temporary screenshot was deleted. macOS/Windows contracts remain deferred at the owner's request; Linux local authoritative setting remains unverified.

A real-world app may present one pet setting in the UI; that observation alone does not prove an on-disk, readable, account-wide mirror or consistent revision semantics across apps. Do not interpret per-app local settings as the shared setting, guess an app-data path, read credentials/keychains/chat history, or introduce an undocumented cloud API.
